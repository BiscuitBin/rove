# Maintain dependencies

Runtime dependencies are compatible ranges with a tested lower bound, tools are exact
pins, and `uv.lock` is the pin for the runtime dependencies and the `dev` and `tooling`
groups (not the build backend): committed, generated by `uv lock`, never
hand-edited, and read with `--frozen` by every recipe that checks, so no gate can
rewrite it. This is [decision 0005](../decisions/0005-dependency-policy.md). Renovate
proposes the moves ([decision 0008](../decisions/0008-renovate.md)), but it moves
nothing by itself: every update waits on its dependency dashboard until a maintainer
approves it, and then arrives as a pull request that `check` must pass and a person
must merge. The commands below are how a maintainer makes the same moves by hand.

## What Renovate proposes and what stays manual

`renovate.json` holds the configuration. Every update waits for a tick on the
dependency dashboard issue; Renovate's window is early Monday (UTC).

| Pin | Where | Read by | Pull request |
| --- | --- | --- | --- |
| typer's range | `[project] dependencies` | `pep621` | alone; moves `uv.lock` within the range, and the range only when a release falls outside it |
| coverage, mypy, prek, pytest, ruff | `[dependency-groups] dev` | `pep621` | one per tool, with its `uv.lock` change |
| hatchling | `[build-system] requires` | `pep621` | alone; `pyproject.toml` only, since `uv.lock` does not hold it |
| the shared checkers' tag | `[tool.uv.sources]` | `pep621` | alone, with its `uv.lock` change |
| everything else in `uv.lock` | `uv.lock` | lock-file maintenance | one a week, alone |
| action SHAs and their version comments | `.github/workflows/`, `.github/actions/setup/action.yml` | `github-actions` | `github actions`, one group |
| uv's version | the setup action's `version:` input | `github-actions` | in the `github actions` group |
| just's version | the setup action's `rust-just==` | regex manager | alone |
| hook revisions and their version comments | both prek configurations | regex manager | `hook revs`, one group |
| lychee's revision and both `LYCHEE_VERSION=` | `.pre-commit-config.yaml` | regex managers | `lychee`, one group, all three together |

Two pins stay manual, because [decision 0001](../decisions/0001-uv-and-hatchling.md)
owns them and a new Python is a decision rather than an update: `.python-version`,
the interpreter the tools run on, and `requires-python`, the package's floor. The
`python-version` inputs in `ci.yml` follow those two by hand, and so do the version
floors that [Develop locally](develop-locally.md) states for uv and just.

A bot's pull request is proposed code. Read the diff and the release notes before
merging, above all for a hook revision or the shared checkers: a hook that stops
reporting, or a checker that accepts more, still passes `just check`.

## Check that the lock still matches

```console
just lock-check
```

This runs `uv lock --check --offline`, which never writes. It is the first gate of
`just check`, so a `pyproject.toml` edited without relocking fails the gate rather than
drifting. The project's own version is in the lock too, so a version bump needs a
relock as well.

## Update deliberately

```console
just lock            # relock after editing pyproject.toml
just lock-upgrade    # move every locked version as far as pyproject.toml allows
```

`just lock` runs `uv lock`: it resolves what `pyproject.toml` states and keeps every
locked version that still satisfies it. `just lock-upgrade` runs `uv lock --upgrade`,
which moves every package to the newest version its constraint admits. The `dev` pins
are exact and the shared checkers sit at a Git tag, so those packages hold still, but
everything beneath them moves: typer's runtime tree, and the tools' own dependencies
(pytest's `pluggy` and `iniconfig`, mypy's `mypy-extensions` and `pathspec`, and B's
requirements), so the gate's environment can change too. Both need the network, and both write `uv.lock`. Read the diff before
accepting it, then:

```console
just sync
just check
```

`just sync` installs the new lock into `.venv/`, while the network is there, and
`just check` proves the gate still passes against it.

## Adding or moving a runtime dependency

1. Edit its line under `[project] dependencies` in `pyproject.toml`. The lower bound is
   the version you test against; the upper bound is the next release that may break
   it (the next minor while the dependency is at 0.x).
2. A new dependency carries the note decision 0005 asks for, as a comment beside its
   line and in the pull request: what it does, why the standard library will not do,
   its licence and its maintenance.
3. Run `just lock`, read the diff, then `just sync` and `just check`.
4. If `import rovo` itself needs it, the wheel smoke's first step changes too
   ([decision 0003](../decisions/0003-typer-cli-and-lazy-import.md)).

## The tools

The `dev` group pins coverage, mypy, prek, pytest and ruff exactly, and
`[build-system]` pins hatchling. hatchling is outside `uv.lock`; only its `==` holds
it, and its own requirements resolve afresh in each build
([decision 0005](../decisions/0005-dependency-policy.md)). To move one, edit its `==`
version, run `just lock` (a hatchling bump leaves `uv.lock` unchanged), read the diff, run `just sync` and `just check`. A ruff or mypy upgrade usually
surfaces new findings: fix them rather than pinning back, unless a finding is wrong for
this project.

## The shared checkers

`biscuit-games-tooling` is the `tooling` group, taken from
`https://github.com/steven-cutting/biscuit_games_tooling` at a Git tag through
`[tool.uv.sources]`; `uv.lock` records the commit the tag named. To move it, read that
repository's changelog for the release you are taking, edit the `tag`, run `just lock`,
read the diff, then `just sync` and `just check`. The package supplies the gate runner
and both validators, so a release can fail a tree that passed.

## Security advisories

```console
just audit
```

It runs `uv audit --frozen` over the locked versions. It needs the network, so it sits
outside `just check`.

## Hook and action pins

Every remote hook in `.pre-commit-config.yaml` and `.pre-commit-fix.yaml`, and every
remote `uses:` in `.github/`, is pinned to a full commit SHA with its release tag as a
comment. lychee also carries `LYCHEE_VERSION` at the head of its argument lists, which
must match the comment; Renovate moves the three together, and a hand move must too.
To move a pin by hand, resolve the release tag to its commit (an annotated tag's
reference names the tag object, not the commit), and replace the SHA and the comment in
every file that names it.
