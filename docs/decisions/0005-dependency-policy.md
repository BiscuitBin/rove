# Decision 0005: Dependency policy: compatible ranges for runtime, exact tools, `uv.lock` the pin

Adapted from alliumpy's decision 0004 at `c8e1a46`.

## Context

`rovo` is a library as well as a command. An application's manifest can be the last
word on its resolution; a library's runtime requirements are constraints every
consumer inherits, and an exact pin there can stop a consumer resolving a dependency it
shares with something else. The tools are different: the gate's verdict depends on each
tool's exact version, so a tool that moves on its own changes what passes.

The gate runner snapshots the worktree between recipes and aborts on any change, so no
recipe may rewrite `uv.lock`.

## Decision

Runtime dependencies, in `[project] dependencies`, are compatible ranges whose lower
bound is a version the gate has run against: today the one entry is
`typer>=0.27.3,<0.28`, with the upper bound at the next minor because typer is still at
0.x. Tools are exact: the `dev` group pins coverage, mypy, prek, pytest and ruff with
`==`, `[build-system]` pins hatchling, and the `tooling` group takes the shared
checkers at a Git tag. `uv.lock` is committed, generated by `uv lock`, never
hand-edited, and is the pin for the runtime dependencies and the `dev` and `tooling`
groups. It does not lock the build backend: uv does not lock build requirements, so
hatchling is pinned only by its `==` in `[build-system]`, and hatchling's own
requirements (`packaging`, `pathspec`, `pluggy`, `tomlkit`, `trove-classifiers`) are
open ranges resolved afresh in each isolated build. Every recipe runs tools through
`uv run --frozen`, and `just lock-check` (`uv lock --check --offline`) fails when the
lock disagrees with `pyproject.toml`.

A new dependency arrives with a note, as a comment beside its entry in
`pyproject.toml` and in the pull request: what it does, why the standard library will
not do, its licence, and its maintenance (who releases it and how recently).

## Consequences

The tests and the wheel smoke run against one resolution, the locked one. The lower
bound is tested only while the lock sits on it: today `uv.lock` holds typer at
exactly 0.27.3, and once a relock moves it higher nothing here exercises the floor
again. Nothing updates any pin until the Renovate ticket (T06) lands, so the lock ages
deliberately rather than by neglect, and `just lock-upgrade` is a diff to read, not
noise to wave through. `just audit` checks the locked versions against known
vulnerabilities, but it needs the network, so it sits outside `just check`. The wheel
is not fully reproducible from the lock: two clones can build it with different
versions of hatchling's requirements.

## What would reopen this

A consumer unable to resolve `rovo` beside another package because of the upper bound,
which would argue for a wider range. typer reaching 1.0, after which the bound follows
its major version. The release ticket adding a lowest-direct resolution run, which
would make the floor tested continuously rather than only when the lock sits on it.
